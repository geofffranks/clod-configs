# Code Review Follow-up

Resolve the trusted installed helper at `$POLYTOKEN_CONFIG_DIR/bin/code-review-helper.py` (or an equivalent installation-derived absolute path), verify it exists and resolves outside the target checkout, and fail closed if missing or shadowed by a same-name checkout file. Invoke that trusted helper's `followup` command to validate fixture/gh-shaped follow-up identity and calculate targets. Maintain one append-only record per stable repository/PR review scope. Each record includes identity, prior snapshot digest and base/head/merge-base, latest reviewed head, stable finding IDs/fingerprints, evidence anchors, dispositions, lane coverage, verifier result, and every job ID/terminal state.

A follow-up always resolves current head and captures a complete new metadata/diff snapshot. Review only unresolved prior findings plus hunks changed since the prior reviewed head, with bounded context needed to verify them; never silently run a full review or call a partial run clean. Dispositions are exactly `still_present`, `resolved`, `unknown`, or `no_longer_applicable`. Mark resolved only with current-source evidence.

Journal protocol is one canonical JSON object per line, appended atomically as one write with a trailing newline and a per-run reference. Reconcile the valid prefix, but a truncated tail or corrupt record is `blocked`; never truncate or repair in place. Missing/corrupt journal, identity mismatch, base or merge-base change, force-push, unmappable history, materially changed requirements/metadata, incomplete capture, failed lane/verifier, or moving head returns `blocked` with an explicit reason and requests a labeled new baseline or operator decision.
